# lidx call graph against compilers

Generated by `benchmarks/oracle/run.py`. lidx `lidx 0.7.0`, built from main `5ac71c698e` (2026-10-13). Method, toolchains and caveats: [README.md](../README.md).

Each cell is lidx's resolved CALLS edges graded against the answer a compiler gives for the same checkout, at the commits and scope repowise pins for the same cells. Intervals are 95% Wilson.

## Head-to-head with repowise

Every row grades lidx the way repowise grades its own tool, so the verdicts are neither flattered nor penalised by scope. Precision = lidx edges the compiler confirms / lidx edges the compiler can judge. Recall = compiler edges matched (dispatch edges included) / **all** in-scope compiler edges, capture gaps and unindexed callees charged to lidx: the denominator repowise uses. The scope differences handled here:

- **TypeScript**: repowise's `tsc` oracle emits no call made outside a function (module level) and withholds every call resolved to an abstract target (interface or type-literal member, abstract method, function-typed field), together with the function that makes it. The TypeScript rows drop the same edges from the denominator and leave those callers unjudged for precision. The stricter grading is in the diagnostic table below.
- **Rust**: repowise excludes test files by path only (`tests/` or `test/` directories) and keeps `#[cfg(test)]` code. The `path_tests_excluded` cell does the same. The `#[cfg(test)]`-excluded cell is in the diagnostic table.
- **Go**: repowise counts `calls` edges keyed (caller declaration, callee declaration), keys a dynamic call at the concrete implementation RTA names and never expands an interface method into its implementations. The Go rows grade lidx the same way, on its `CALLS` edges only: a call lidx binds to the one (or the proven) implementation is graded against the concrete callee RTA names, and a call it can only leave on the interface method is a `DISPATCH` edge, not a call, so it is not graded. The "dispatch-credited, lidx-native" table below also credits the `DISPATCH` edges. Closure callees are keyed at the enclosing declaration here and at the literal in repowise, see the README.

repowise columns are their published point estimates (`docs/BENCHMARKS.md`, repowise main, 2026-10-03) with Wilson intervals computed by us from the edge counts of the same cells in repowise-bench. **ahead / tied / behind compares the two 95% intervals** (ahead: lidx's lower bound is above repowise's upper bound; behind: lidx's upper bound is below repowise's lower bound; otherwise tied), never the point estimates.

### Counting rules in one place

- Oracle edges are distinct (caller declaration, callee declaration) pairs; lidx edges are deduplicated the same way.
- Callee outside the repository: not judged on either side.
- **Dispatch edges** (call through an interface or type-literal member, an abstract method, a function value, a trait method) are reported by the compiler as *possible* targets. They stay in the comparable recall; the static-recall column leaves them out.
- Oracle edge whose caller or callee is not a symbol lidx indexes (macro-generated Rust functions, nested functions): reported as a **capture gap** with its reason, out of the static recall, in the comparable recall denominator.
- lidx edge the compiler could not judge (caller file or function not in the analysed program, callee file not analysed, or a call site the compiler left unresolved): not counted for precision, listed under *ungradable*. The unresolved-site exclusion is the one that can flatter lidx; the per-cell lines below give precision if those pairs were counted wrong.
